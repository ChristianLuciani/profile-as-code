# GitHub Profile README — skill de comunicación

## Misión

Convertir los HECHOS del workspace (SSOT) en una página de perfil que se lea en
**30 segundos** con una impresión fuerte: quién sos, qué estás construyendo AHORA,
por qué importa, y UNA acción posible. El dump exhaustivo ya lo produce el renderer
determinista (`pasco build`) — esta skill es la capa de **juicio y narrativa** (D4/D5).

## Regla de oro

> Los HECHOS son sagrados (byte-idénticos al SSOT); solo la HISTORIA varía.

- Nombres, fechas, DOIs, números, URLs: **idénticos** a `content/*.yaml`. Prohibido
  inventar, redondear o reordenar hechos.
- URLs SOLO de `identity.links` (regla drift). No inventes links.
- Claims cuantitativos SOLO de `projects[].evidence` o `keywords.geo.claims`.

## Fuente de datos

Lee el workspace (ruta del `.pascorc` o `--workspace`):

```
content/identity.yaml      → nombre, ubicación, links canónicos (TU fuente de URLs)
content/positioning.yaml   → statement + ángulos por audiencia + anclas GEO
content/projects.yaml      → qué construís (status + evidence verificable)
content/publications.yaml  → papers/preprints con DOI
content/skills.yaml        → stack con pesos por plataforma
content/bios.yaml          → textos base por plataforma (punto de partida)
content/keywords.yaml      → SEO + GEO (associations/claims)
```

## Estrategia comunicativa (framework de 3 preguntas — SOTA-2026 §3)

1. **¿Quién lee?** Contribuidores OSS, sponsors, reclutadores técnicos, pares.
2. **¿Qué quiero que hagan?** Explorar los proyectos, sponsor (Patreon/GitHub Sponsors),
   contactar para colaborar/contratar.
3. **¿Cuál es mi señal más fuerte?** Para un perfil open-source/soberanía: el trabajo
   público con evidencia (upstream PRs merged, papers con DOI, deployments probados).

Liderá con #3 filtrado por #1: **stewardship** (proyectos vivos con proof), no branding.

## Estructura del README (prosa, no dump)

1. **Header**: nombre + one-liner que responde "qué construís" (de `statement`/headlines,
   reescrito en prosa si mejora) + badges canónicas (identity.links) centradas.
2. **Hook** (2–3 líneas): quién sos y por qué lo que hacés importa — conectá física +
   sistemas complejos + IA soberana como UNA historia, no como lista. Weave de las
   anclas GEO (`positioning.geo.semanticAssociations`) de forma natural, sin stuffing.
3. **Qué estoy construyendo AHORA** (2–3 proyectos con narrativa): nombre, una frase de
   valor (de `description`), UNA evidencia verificable (de `evidence[]`). Prosa corta,
   no bullets de 4 items. Prioridad por `skills[].platformWeights[github-readme]`.
4. **Evidencia de stewardship** (una sección corta): upstream PRs (merged/open) y
   papers con DOI — woven como "every merged PR is infrastructure that belongs to
   everyone". Tabla compacta si son varios.
5. **Stack como señal**: 4–6 tecnologías reales de `skills` (los keywords de mayor peso),
   no todos los que tocaste. Badges shields.io máximo ~8.
6. **UN CTA**: Patreon (soporte al trabajo) + UN link más (CV o contacto). No cinco.
7. **Footer**: firma visual (one-liner o ASCII art sutil, coherente con la identidad) +
   `<!-- generated by profile-as-code pasco refine github-readme · variant <id> -->`.

## Estética (SOTA-2026 §6)

- **Dark-first**: assets y badges que funcionen en dark mode (GitHub sigue el tema del
  sistema). Nada de fondos claros forzados.
- **Restraint**: máximo un widget de stats (o ninguno si los repos hablan solos);
  cero typing-animations, cero visitor counters, cero snake games.
- **Jerarquía visual**: headers claros, whitespace, una sola columna. `<details>`
  accordions para material secundario si hace falta.
- **Centrado HTML div** para el header/badges en pantallas anchas.
- Tipografía: sin emojis decorativos; símbolos funcionales (✓ mergeado, ↗ link) como
  máximo.

## Variantes (flujo refine)

- Producí **N variantes** (`--variants N`, default 3) con ángulos distintos:
  1. **Stewardship** (por defecto): lidera con open source + evidencia.
  2. **Soberanía**: lidera con la tesis (IA soberana, economía agéntica), proyectos como prueba.
  3. **Investigador**: lidera con publicaciones/DOI, proyectos como aplicación.
- Cada variante: `variantId` = `githubreadme-<lang>-<n>` (ej. `githubreadme-en-1`).
- El humano elige; se registra con `pasco refine github-readme --choose <id>` →
  escribe `content/active.yaml`.

## Verificación (checks)

- `pasco validate` exit 0 (schema + drift 0 + geo).
- Facts byte-idénticos: cruzá cada hecho del README contra el YAML.
- Links ⊆ `identity.links` (más el hecho de contacto: fila `- [Email](mailto:…)` derivada
  de `identity.email`, v1.5/#71 — primero en `## Links`, output-only, nunca en `sameAs`).
- Length: el README se lee en 30s (SOTA-2026 §1) — si hay más de ~40 líneas, recortá.
- CTA: exactamente una acción primaria.

## GEO (consistencia = citabilidad)

- Los hechos del README deben coincidir byte a byte con el CV y LinkedIn (fechas,
  roles, papers) — un LLM que triangula y encuentra contradicción te descarta.
- Los anchors semánticos se refuerzan naturalmente en la prosa (no keyword stuffing:
  los LLM lo descuentan, SPEC §8 anti-patterns).
