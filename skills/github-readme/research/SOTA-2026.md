## 1. El problema central: señal, no ruido

El error N°1 es tratar el README como un **resumen de CV**: listas largas de tecnologías,
paredes de badges, GIFs animados. Los reclutadores piden "signal, not noise"
[EXPERTO — Codeboards.io, "GitHub Profile README Guide 2026", 2026].

- Un visitante decide en **~6 segundos** si explora más [EXPERTO — Igor Braz, dev.to,
  "Top 10 Hacks... 2026", 2026-08-06].
- Reclutadores técnicos pasan **30–90 segundos** en un perfil de GitHub; la meta es
  **comprensión en 30 segundos, no completitud** [EXPERTO — Quillly/devbio.me,
  "GitHub Profile README: What to Include in 2026", updated 2026-06].
- El 82% de las contribuciones ocurren en repos privados [OFICIAL — GitHub Octoverse 2025]
  → el perfil público muestra <20% del output real; el README debe **dirigir a la mejor
  evidencia pública**, no intentar listar todo.

## 2. Los 8 elementos que funcionan (2026)

[EXPERTO — Quillly/devbio.me, 2026-06]

1. **Bio de una línea** que responde "qué construís", no el cargo ("passionate developer"
   no funciona).
2. **Stack como señal, no como lista**: 3–5 tecnologías en las que sos genuinamente
   experto. TS es #1 en GitHub desde ago 2025 (+66.6% YoY, Octoverse 2025) — decirlo
   explícito si aplica.
3. **Un widget de stats** (dark-themed, que matchee el perfil). Ojo: los contadores de
   contribuciones se están inflando por herramientas de IA (1M+ PRs generados por IA
   entre may–sep 2025 [OFICIAL — Octoverse 2025]) → volumen es señal más débil.
4. **Heatmap de contribuciones** (consistencia > estallido).
5. **Repos pineados con contexto**: una frase de qué hace, no solo el nombre.
6. **Qué estás construyendo AHORA** (momentum — da razón concreta para contactar).
7. **UN link** deliberado (el que cuente la historia completa más rápido).
8. **UN número honesto** (stars, usuarios, deployments) — más credibilidad que prosa.

### Qué NO incluir

- Texto animado de typing ("I'm a developer who loves to code…") — el equivalente de un
  spinner; todo generador lo produce [EXPERTO — Quillly, 2026-06].
- Contadores de visitas (se inflan, no dicen nada).
- "Currently learning X, Y, Z" (señal de que no estás haciendo bien ninguno).
- Párrafos largos de bio (nadie los lee).
- Skills en prosa ("team player") — cero señal.

## 3. El framework de las 3 preguntas (antes de escribir)

[EXPERTO — Quillly, "10 Templates (2026)", 2026-06]

1. ¿Quién lee esto? (reclutador, contribuidor OSS, cliente, co-founder)
2. ¿Qué quiero que hagan? (contratar, abrir un PR, bookear una llamada, sponsor)
3. ¿Cuál es mi señal más fuerte? (años, repos con stars, revenue, papers)

El README lidera con la respuesta a #3, filtrada por #1. No se puede hablar a 180M de
desarrolladores a la vez — **un patrón, una audiencia**.

## 4. Patrón recomendado: The OSS Maintainer (stewardship)

Para un perfil alineado a **open source + soberanía tecnológica**, el patrón OSS
Maintainer es el correcto [EXPERTO — Quillly, Pattern 2, 2026-06]:

- Señal de **stewardship**, no branding personal: contribuidores potenciales revisan el
  perfil ANTES del código.
- Elementos: proyectos activos con descripción de una frase + evidencia; widget de stats
  o heatmap; **CTA de sponsorship** (GitHub Sponsors / Patreon / Polar); links de
  comunidad.
- "One founder documented how consistent public proof of project activity was the
  turning point from zero to five-figure MRR — the README is the most visible piece of
  that proof" [EXPERTO — Indie Hackers, citado en Quillly, 2026-06].

Variante "minimalista senior" [EXPERTO — Quillly, Pattern 5]: tres cosas claras > veinte
vagas; cada palabra gana su lugar; funciona cuando los repos pineados son fuertes.

## 5. GEO — cómo leen los LLM el perfil de GitHub

- El README del perfil es **contexto de agente**: un LLM que triangula una identidad
  cruza GitHub ↔ LinkedIn ↔ web. Hechos inconsistentes = auto-descarte [INF — SPEC §8].
- La consistencia factual entre superficies ES citabilidad: fechas/roles/papers idénticos.
- Structured data: el JSON-LD `Person` (sameAs = links canónicos) ayuda a la resolución
  [INF — schema/README.md, geoCheck structured-data readiness].

## 6. Estética (2026, lo que funciona)

- **Dark-first**: el widget de stats y los assets deben matchear dark mode
  [EXPERTO — dev.to Igor Braz, hack #9: SVG con media queries de prefers-color-scheme].
- **Centrado HTML div** para header/badges en pantallas anchas [EXPERTO — dev.to, hack #10].
- **Accordions `<details>`** para material secundario (setup, certificaciones) — mantiene
  limpio el primer scroll [EXPERTO — dev.to, hack #6].
- **Restraint**: un solo widget de stats; paredes de badges = señal de optimización en
  vez de construcción [EXPERTO — Quillly, 2026-06].
- **ASCII art / one-liner** como firma visual funciona si es parte de la identidad
  (perfil senior), no un decorado [BENCHMARK — patrón observado en perfiles técnicos].
