# Substack — platform research (2026-11-05)

Scope: what Substack actually is as a *surface* — profile, publication, About
page, monetization, distribution, API — so the engine can decide what the SSOT
models and what it deliberately leaves out.

Method: every source below was fetched 2026-11-05 (UTC). Substack's help center
is Cloudflare-challenged for plain fetch (HTTP 403); official pages were read
through the `r.jina.ai/<url>` reader mirror and are tagged `[WEB]` with the
official URL kept. Third-party analyses are tagged `[EXPERTO]` and dated. Our own
engine runs are `[BENCHMARK]`.

Tiers: `[OFICIAL]` = Substack's own pages/help center · `[EXPERTO]` = a dated
third-party analysis · `[BENCHMARK]` = a measurement of this repo's engine ·
`[?]` = not documented / not calibratable.

---

## 0. The one structural fact: Substack is three surfaces under one slug

The platform slug `substack` hides three products:

1. **Profile** — the social identity: `substack.com/@handle`, name, photo, bio,
   links, reads/likes, private mode.
2. **Publication** — the website + newsletter: name, short description, hero
   text, logo/wordmark/cover, About page, welcome page, theme, sections, custom
   domain, email sender/footer, podcast feed.
3. **Monetization** — subscriptions: monthly/annual plans, founding tier, group
   plans, trials, coupons, gifts, pledges, access levels, fees, analytics.

A fourth layer, **distribution** (Notes, Chat, DMs, comments, recommendations,
leaderboards), is where the social graph lives. D23 already calls this
`distribution`, not a profile body.

This is the source of most of the modelling friction: the engine's renderer
contract is **one artifact per platform**, while Substack publishes *at least*
two identity-bearing bodies (profile bio + publication About).

## 1. Profile surface

`[OFICIAL]` [How can I publish on Substack?](https://support.substack.com/hc/en-us/articles/29152946791188-How-can-I-publish-on-Substack) (updated 2026-11-05)

| Field | Where it appears | Notes |
|---|---|---|
| Handle | `substack.com/@handle`; mentions in notes/posts | Unique at signup; profile URL is derived from it |
| Display name | Profile header | Editable at `substack.com/profile/edit` |
| Bio | Profile header | Editable at `substack.com/profile/edit` |
| Social media / website links | Profile | Added in the same edit screen |
| Photo | Profile | — |
| Posts tab | Profile | Shows posts **unless** the publication is in private mode |

Treat that as an editorial soft cap, never a hard rule.

### 2.2 Website editor (design layer)

`[OFICIAL]` [features](https://substack.com/features) · [customization guide](https://on.substack.com/p/guide-website-customization-organization)

- Homepage layouts: **profile** (mirrors your Substack profile), **newspaper**,
  **magazine**, **custom**.
- Colors, fonts, custom header/footer, hero/banner alignment, content blocks,
  navigation editor, sidebar links, section organization (archived sections),
  section-level themes, drop caps, prev/next toggles, preview-image crop.
- Custom static pages: About, FAQ, or any page.
- Welcome page customization (including hiding the description when a cover
  image is used).
- Custom domain: one-time **$50 USD**, a subdomain (`www.…`) is required, root
  domain is a 301 redirect, CNAME → `target.substack-custom-domains.com`,
  verification up to 36 h; **email still sends from `@substack.com`**
  `[OFICIAL]` [custom domain article](https://support.substack.com/hc/en-us/articles/360051222571) (updated 2026-10).

This layer is presentation, not identity: it is not a fact about the person or
brand, it cannot be rendered deterministically from a text SSOT, and it changes
without the SSOT changing.

### 2.3 Post-level SEO

`[OFICIAL]` [SEO guide](https://on.substack.com/p/substack-seo-guide) (2023-02-15)

Per post: **SEO title**, **SEO description**, **URL slug**, **social preview
image**. Defaults come from the title/subtitle/first image. The guide
*recommends* a title tag under 60 characters — a guideline, not a platform cap.

## 3. Monetization surface

### 3.1 Plans and prices

`[OFICIAL]` [set up a paid publication](https://support.substack.com/hc/en-us/articles/360037459952) (updated 2026-11-02) · [founding members](https://support.substack.com/hc/en-us/articles/360042039091) (updated 2026-04-21) · [change price](https://support.substack.com/hc/en-us/articles/360037829591) (updated 2026-11)

- **Free to start**; paid subscriptions enabled from Settings → Payments (Stripe
  Connect).
- **Monthly** and **annual** plans; there is **no yearly-only** option.
- Minimum price in USD: **$5/month** and **$30/year** (other currencies vary
  with the Stripe account).
- **Founding member plan**: a custom price **above** the annual plan; optional
  *flexible founding pricing* lets readers pay between annual and founding;
  founding-only posts and a dedicated welcome email exist. Removing the plan
  does not change existing founding subscriptions.
- **Group subscriptions** and group offers (per-seat / custom), gift
  subscriptions, free trials, coupons/discounts, multi-currency, Apple IAP,
  pledges, paywall unlock tokens, cancellation offers, subscriber perks, manual
  invoicing `[OFICIAL]` features page.
- Revenue share: **writers keep 90%** of revenue minus credit-card fees; the
  platform takes 10% `[OFICIAL]` [going paid](https://substack.com/going-paid).
  Stripe's processing fee stacks on top `[EXPERTO]` [LetterDuck pricing analysis](https://letterduck.com/pricing/substack)
  (2026-08-18, competitor — use only for the fee arithmetic, not for the verdict).

### 3.2 Access levels and paywall

`[OFICIAL]` features page · [free preview article](https://support.substack.com/hc/en-us/articles/4407989020308) (updated 2026-10)

- Four post access levels: **Free (everyone)**, **Free subscribers only**,
  **Paid subscribers only**, **Founding members only**.
- A paywall break can be placed anywhere in a post; a paid post can be sent as a
  **free preview** to free subscribers; the preview label persists as history.
- Paywall *header* customization is email-only; the web paywall is platform UI.

### 3.3 Analytics

Subscriber dashboard with ARR, cohorts/retention, open/click rates, post-level
stats, traffic sources, revenue; CSV export `[OFICIAL]` features page. The
official Publisher API exposes a read-only subset (see §5).

## 5. API reality (write vs read)

There are **two different API stories** and conflating them is the easy mistake:

| Surface | Status | Capability | Evidence |
|---|---|---|---|
| `publisher-api.substack.com/v1` | **Official, opt-in/gated** | Read-only: list/get posts, post stats, subscriber counts, subscriber lookup; `authorization: <api_key>`, per-publication key from Settings → Publisher API | `[EXPERTO]` [API ecosystem research, 2026-05-09](https://github.com/mvanhorn/printing-press-library/blob/73270e0f86b4d78da4f9cb49e380fd312b65758e/library/media-and-entertainment/substack/.manuscripts/20260509-103230/research/substack-ecosystem.md) + [publisher MCP README](https://github.com/dkships/substack-publisher-mcp) |
| `<pub>.substack.com/api/v1` and `substack.com/api/v1` | **Unofficial / internal** | Drafts, publish, schedule, image upload, sections, tags, Notes, comments | `[EXPERTO]` same research (8+ reverse-engineered clients) |
| Public post API | **None** | — | `[EXPERTO]` [Kin Lane, 2026-10-15](https://raw.githubusercontent.com/api-evangelist/posts/main/_posts/2026-10-15-commune-has-an-api-and-substack-does-not.md): "Substack does not offer a public API" |

Consequence for this repo: the declared `deploy: manual` (D9) stands — there is
no public body-publish API. A future *verification* path (not deploy) could read
the Publisher API, but it is gated and read-only, so it cannot replace the paste
checklist.

Auth reality for any internal-API idea: session cookie (`substack.sid`), captcha
on password login, Cloudflare on public read paths — high breakage
`[EXPERTO]` same research, §5.

### 7.1 Empirical checks

- `[BENCHMARK]` A person workspace declaring `newsletter` **validates**
  (`pasco validate` exit 0). JSON Schema has no flavor conditional, so the block
  is accepted; SPEC §17 documented it as brand-only until #481 made it
  flavor-neutral.
- `[BENCHMARK]` With no renderer, `pasco build substack` falls back to the shared
  paste source and emits **only the `long` bio** (`profiles/substack.md`). There
  is no publication sheet today — name, short description and About logistics
  never leave the SSOT.
- `[BENCHMARK]` `compile()` passes `newsletter` and `podcast` through **raw**
  (langMaps unresolved), unlike `bios`/`headlines`. A Substack renderer resolves
  them with core's exported `textOf(map, lang)` (#415) — the helper exists; the
  compile seam simply does not apply it to the publication block.

### 7.2 The gaps (G1 resolved by #481)

**G1 — a person can own a publication, and the contract now says so.**
`newsletter` (and `podcast`) were introduced in SPEC §17 as *brand* blocks even
though the schema never had a flavor conditional. #481 made them flavor-neutral;
the remaining work is the renderer (#483) and the profile skill (#482).

**G2 — the post contract does not carry the access level.**
Substack's four access levels are a publish-time property the paste checklist
must state. `skills/substack/longform.yaml` declares fields, word band and
`export: paste` but no `access`. Adding `access: free | free-subscribers | paid |
founding` (optional, default `free`) is small and directly useful; it requires
a `pasco post` change (not a schema change).

**G3 — no Substack *profile* skill bundle.**
`skills/substack/` ships the long-form post skill only (`SKILL.md`, `post.md`,
`longform.yaml`). Every profile platform in this repo ships `research/`,
`checks.yaml`, `playbook.md`. The absence is why `renderer: false` and why no
caps exist.

## 8. Deliberate exclusions (recommended)

These stay out of the schema and the renderer, with a reason each:

1. **Design layer** — theme, colors, fonts, nav, sections, layouts. Not
   identity; non-deterministic from text; the operator designs it once.
2. **Billing** — plans, prices, currency, trials, coupons, gifts, fees, taxes,
   payouts. Stripe/Substack is the source of truth; duplicating it in the SSOT
   guarantees drift and needs money/time semantics the engine does not have.
3. **Analytics** — subscribers, ARR, opens, clicks. A read surface that changes
   daily; the Publisher API (or a future adapter) reads it, the SSOT never stores
   it.
4. **Rich About composition** — testimonials, embedded video, images,
   highlighted posts, special offers. Editorial page assembly, not facts.
5. **Account/privacy settings** — private mode, likes/reads visibility, AI
   training protection. Checklist steps, not identity.
6. **Distribution** — Notes, Chat, DMs, comments, recommendations. D23
   `distribution`; copy lives in skills.

What the engine *should* own from Substack: the identity body (name, handle,
bio, photo, links), the publication's textual identity (name, short description,
About body, cadence, canonical URL), and the deploy/verification state.

## 9. Recommended v1 scope

**A Substack paste sheet, not a site builder.** One deterministic artifact per
workspace+lang, `deploySpec: manual`, built from existing fields:

```
# Substack — <name> (<lang>)
Handle: @<handle>                     ← identity.handle / socialHandles
Display name: <identity.name>
Bio (profile, soft cap): <bios short>
About (publication + person): <bios long>
Links: <identity.links — SSOT only>
Publication: <newsletter.name>
Short description: <newsletter.description>
Cadence: <newsletter.cadence>
Canonical: <newsletter.url>
```

Then the operator pastes field by field and `pasco status --mark substack`
records the deploy. This needs **no schema change** and is a strict improvement
over today's single-bio fallback.

Decisions taken (2026-11-05, operator): **one paste sheet** artifact (not separate
profile/About artifacts); `newsletter`/`podcast` become **flavor-neutral** in SPEC
§17; the post contract carries **`access`**. The caps question stays open — soft
caps in `checks.yaml` marked `[?]` only if the skill bundle needs them.
